# Out-of-Hours Call Log & Review Dashboard — Build Spec
For: Jewel Home Support
Prepared: 11 August 2026
Companion to: `Out-of-Hours-Call-Transcript-Improvement-Report.md`, `Out-of-Hours-Call-Log.xlsx`

---

## 1. Purpose

Replace the current email-based call record system with a structured, searchable database and review dashboard for out-of-hours calls handled by the voice agent ("Kath"). The system should make it easy to see, at a glance, which calls need human attention — without anyone having to read every transcript email.

This spec is based on a review of 47 real call transcripts (see the companion report) which surfaced recurring problems: garbled postcodes, caller/client identity confusion, mishandled emergencies, occasional AI-fabricated call summaries, and a meaningful rate of dropped/incomplete calls.

## 3. Ingestion

- Calls currently arrive as emails to `voiceagent@jewelhomesupport.co.uk`. The simplest v1 ingestion path is parsing these emails (via a scheduled job or webhook) into the `calls` table using the existing 4-part template (Caller Name / Phone Number / Reason of Call / Transcript).
- Longer term, ingesting directly from the voice platform's API/webhook (if the provider offers one) would be more reliable than parsing emails.

---

## 4. Auto-Flagging Rules (v1, rule-based — not ML)

Run against each new `calls` row on ingestion:

- **`incomplete_transcript`** — transcript has fewer than N exchange turns, or ends immediately after the agent's opening line.
- **`ambiguous_safety_answer`** — a yes/no-style answer near a safety/triage question (e.g. "conscious and breathing") contains contradictory tokens (e.g. both "yes" and "no" close together).
- **`low_confidence_address`** — address/postcode field doesn't match a valid UK postcode format, or contains non-postcode filler words.
- **`safeguarding_keyword`** — transcript contains terms like "neglect," "unsafe," "hasn't come," "hurt," "abuse," "safeguarding."
- **`agent_loop_detected`** — the same agent question appears 2+ times in a row without a new caller answer in between.
- **`possible_fabricated_summary`** — `ai_summary` contains named entities (people, places, requests) that do not appear anywhere in `raw_transcript`. This is the highest-priority flag type given the two confirmed cases in the review — treat any unverified entity in the summary as a hard flag, not a soft one.
- **`human_requested`** — transcript contains phrases like "speak to a person," "not a robot," "real person."

Urgent flag types (`ambiguous_safety_answer`, `safeguarding_keyword`, `possible_fabricated_summary`) should trigger an immediate notification (SMS/call to on-call manager), not just appear in a dashboard queue.

## 5. Dashboard (v1 scope)

- **Call list view** — sortable/filterable table (mirrors the columns in `Out-of-Hours-Call-Log.xlsx`): date, time, phone, caller, client, category, urgency, flags, severity.
- **Call detail view** — full structured fields + raw transcript + list of flags with review status.
- **Review queue** — flagged, unresolved calls only, sorted by severity/urgency, with a way to mark reviewed and add notes.
- **Known issues page** — list of `known_issues`, their status, and linked example calls.
- **Config changes log** — list of `agent_config_changes`, with a manual "mark reviewed for effectiveness" action.
- **Summary stats** — counts by category/severity/flag type (as in the Summary tab of the xlsx), ideally with a simple trend view over time once enough data accumulates.

## 6. Non-functional requirements

- **Data sensitivity**: this system holds vulnerable adults' personal and sometimes health-adjacent data (e.g. hospitalisation mentions, a date of birth was volunteered in one real call). Access should be restricted to authorised staff, and hosting/storage should meet UK GDPR requirements for care-sector data.
- **Audit trail**: `raw_transcript` and `agent_config_changes` should be immutable/append-only — this is a record staff and regulators may need to review later.
- **No autonomous model retraining**: per the companion report, the system should NOT attempt to auto-learn or fine-tune the voice agent from stored call data. Improvement happens through the human review → known issue → config change → effectiveness check loop in Section 10 of the report, not automatically.

---

## 7. Suggested build order

1. **Schema + manual data entry** — stand up the database with the tables above; backfill from the `Out-of-Hours-Call-Log.xlsx` sample as seed/test data.
2. **Email ingestion** — automate pulling new calls from the voiceagent@ inbox into `calls`.
3. **Auto-flagging rules** — implement Section 4's rules against new rows.
4. **Dashboard v1** — call list, detail view, review queue.
5. **Alerting** — SMS/call trigger for urgent flag types.
6. **Known issues + config change log** — close the improvement loop described in Section 10 of the companion report.
